.. _rendered-yaml:

The rendered workshop definition
================================

``.workshop/<name>.yaml`` is the contract between this repository and the
Workshop snap: the rendered definition ``workshop launch <name>`` consumes.
It is **generated** - never hand-edit it.

The contract
------------

- **Generated by** ``scripts/render.sh`` from
  ``profiles/<profile>/workshop.yaml.j2`` plus the merged variables
  document, rendered with jinja2.
- **Filename equals the instance name**: rendering ``sunbeam`` writes
  ``.workshop/sunbeam.yaml``, rendering ``packaging-foo`` writes
  ``.workshop/packaging-foo.yaml``. Post-validation parses the YAML,
  requires the top-level ``name:`` to equal the requested name, and
  requires a ``base:`` key; the target file is never written when
  validation fails.
- **Gitignored** (``.workshop/*.yaml``), while the tracked sources under
  ``.workshop/<profile>-tools/`` (the in-project SDKs) stay versioned.
- **Atomically published**: the render lands in a temporary file inside
  ``.workshop/`` and is renamed into place, so readers never see a partial
  file.
- **Idempotent**: re-rendering the same name overwrites deterministically.
- **Shadow warning**: when a ``profiles/<name>/`` directory exists
  alongside a launched instance of the same name, the render succeeds but
  warns - the profile now shadows the instance.

To change a rendered definition, edit the profile template or variables
and re-run ``just render <name>``. CI renders the bounded name matrix in
``scripts/ci/render-matrix.sh`` and validates each output against the
vendored schema (``scripts/check-render.sh``), so a hand edit is both
overwritten and detected.

Anatomy of a render
-------------------

This is the ``sunbeam`` render with comments stripped; ``base`` and the
SDK chain come from the template, and ``name`` from the requested instance
name:

.. code-block:: yaml

   name: sunbeam
   base: ubuntu@26.04
   sdks:
   - name: system
     slots:
       github-token:
         interface: secret
         attributes:
           service: "gh:github.com"
           username: ""
       openrouter-key:
         interface: secret
         attributes:
           service: "openstack-workshop-openrouter-key"

     plugs:
       mcp-oauth-callback:
         interface: tunnel
         endpoint: localhost:19876

   - name: opencode
   - name: openchamber
     channel: latest/edge
   - name: gh-cli
   - name: uv
     channel: latest/stable
   - name: project-sunbeam-tools
     plugs:
       ssh-agent:
         interface: ssh-agent
       openrouter-key:
         interface: secret
   connections:

   - plug: gh-cli:github-token
     slot: system:github-token
   - plug: system:mcp-oauth-callback
     slot: opencode:opencode-mcp-oauth-callback
   - plug: sunbeam-tools:openrouter-key
     slot: system:openrouter-key

The pieces:

.. list-table::
   :header-rows: 1

   * - Element
     - Meaning
   * - ``name`` / ``base``
     - The instance name and the base image (``ubuntu@26.04``).
   * - ``system`` slots
     - Two **secret slots** naming host keyring items by lookup attributes, never the values: ``github-token`` (``service: "gh:github.com"``, ``username: ""`` for gh's current account) and ``openrouter-key`` (``service: "openstack-workshop-openrouter-key"``, the item ``just secret-setup`` stores).
   * - ``system`` plugs
     - ``mcp-oauth-callback`` is a **tunnel plug** forwarding ``localhost:19876`` from the host so the Atlassian OAuth redirect reaches opencode inside the workshop.
   * - SDK chain
     - ``opencode``, ``openchamber`` (``latest/edge``), ``gh-cli``, ``uv`` (``latest/stable``), then the in-project ``project-<profile>-tools`` SDK; a profile's ``extra_sdks`` land between ``uv`` and the project SDK (packaging inserts ``orange-dev-tools``).
   * - ``ssh-agent`` / ``openrouter-key`` plugs
     - Both grafted onto the project tools SDK. The ssh-agent plug forwards the host SSH agent for git over SSH (the system slot is implicit, so no connection entry is needed); the ``openrouter-key`` secret plug delivers the OpenRouter key to the hooks that write opencode's ``auth.json``.
   * - ``connections``
     - ``gh-cli:github-token`` connects to the system secret slot and ``<profile>-tools:openrouter-key`` to the system ``openrouter-key`` slot (both manual connections completed by ``just secret-setup <name>``); the system tunnel plug connects to the opencode SDK's OAuth callback slot.

A suffixed instance renders the same template with its own name - the
``packaging-foo`` render is identical in structure except for
``name: packaging-foo``, the ``orange-dev-tools`` SDK entry, and
``project-packaging-tools``.

Companion state
---------------

``just setup`` also persists the merged variables document to
``.state/<name>.vars.json`` (mode 0600, under the gitignored ``.state/``
directory). The provisioning hooks read the git identity from it; it is the
only per-instance state the setup writes besides the rendered definition
itself.
