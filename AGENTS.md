## Overview

This repository (`sunbeam-workshop`) turns a fresh Ubuntu 24.04+ amd64 host
into named, isolated OpenStack development workshops: LXD containers launched
by the Workshop snap from rendered definitions under `.workshop/`. Profiles
are data, not code - a jinja2 template plus variables per profile - so new
profiles and renamed instances never require programming. Three profiles ship:
`sunbeam` (charm/snap/rock craft toolchain, tox, optional sidecar VM),
`charmed` (classic charm toolchain, git-review for Gerrit), and `packaging`
(Ubuntu packaging on the orange-dev-tools SDK). A free-form suffix
instantiates the same profile under a new name (`just setup packaging-foo`).

Every profile declares the same AI/tooling SDK chain: opencode, openchamber
(`latest/edge`, serves the UI on :3000), gh-cli (token from the host keyring
via a secret plug), uv, then the in-project `project-<profile>-tools` SDK
carrying this repo's hooks. The Atlassian (Jira) MCP server is seeded into
the opencode config by `setup-project`, and
`canonical/openstack-agentic-skills` is cloned and symlinked into the
opencode skills directory. There is no omp, no vscode, and no herdr anywhere
in this repo - that is deliberate scope, not a gap.

## Core Engineering Practices

the repository root. Load the matching skill before doing the work:

## Agent Runbook

You typically operate either on a host checkout of this repo or **inside a
launched workshop container**, where `$USER` is `workshop` and this repo is
mounted at `/project`. Working clones of the profile repositories live under
`/project/git/`. Host-mutating recipes are guarded and abort inside the
container (Invariant 4), so the same command list is correct from either
side, and the dangerous ones only work where they must.

### Common just recipes

| Recipe | Effect | Guard |
| --- | --- | --- |
| `just` | List every recipe | - |
| `just doctor` / `just doctor sunbeam` | Read-only host prerequisite checks; the `sunbeam` argument adds the sidecar-VM capacity floor (8C/16GiB/100GiB) as warnings | read-only |
| `just setup <name>` | Guided, idempotent 6-step setup of a named instance (`SETUP_YES=1` takes every default) | `assert-host` |
| `just render <name>` | Render `.workshop/<name>.yaml` from the profile template + merged vars | - |
| `just launch <name>` | Launch a rendered instance (`workshop launch` passthrough) | - |
| `just shell <name>` | Interactive shell in a running instance | - |
| `just stop <name>` / `just remove <name>` | Stop / remove an instance | - |
| `just repos` / `just repos <profile>` | Clone or update the per-profile checkouts under `/project/git` (github, opendev+Gerrit, launchpad) | `assert-host` |
| `just secret-setup` / `just secret-setup <name>` | Store the GitHub token in the host keyring, log in host `gh`, wire the instance's gh-cli secret plug | `assert-host` |
| `just vm-create` / `just vm-destroy` | Sidecar VM lifecycle (sunbeam profile; destroy keeps `.state/vm/` unless `PURGE=1`) | `assert-host` |
| `just vm-status` / `just vm-shell` | Sidecar VM state (read-only) / ssh shell | - |
| `just lint` | Local twin of the CI lint workflow: shellcheck, hook gate, just-recipe gate, actionlint, config/template validation | - |
| `just test` | Every shell test suite (`scripts/tests/run.sh`; suites discovered live). The pytest unit tests are the separate `python-tests` CI job; locally: `cd scripts && uv run --frozen pytest -q` | - |
| `just docs-build` / `just docs-serve` / `just docs-check` | sphinx-stack docs targets: strict build, local serve, full check battery (D-16/D-17) | - |

### What you may and may not mutate

| Target | Status |
| --- | --- |
| Working clones under `/project/git` | **MAY mutate.** They are the development sandboxes: branch, commit, push to your fork, run tox. |
| Tracked sources (`Justfile`, `just/`, `scripts/`, `profiles/`, `.workshop/*-tools/`, `config/`, `docs/`, `skills/`, `schema/README.md`) | **MAY edit** as normal code changes. Commit deliberately; keep this file in sync. |
| Rendered `.workshop/*.yaml` | **MUST NOT edit.** Generated by `scripts/render.sh`; edit `profiles/<profile>/workshop.yaml.j2` / `vars.json` and re-run `just render <name>` (Invariant 3). |
| `.state/` | **MUST NOT touch.** Runtime state, mode 0700, gitignored: merged vars docs (0600) and sidecar-VM ssh/trust material. Destroying it strands an un-revoked LXD trust certificate. |
| The host keyring | **MUST NOT write.** Only `just secret-setup` (host-side, guarded) stores the token. Containers read it through the connected `github-token` secret plug, never from a file you can see. |
| Host home outside the workshop | **MUST NOT touch.** The container mounts `/project`; anything outside the workshop boundary belongs to the host user. |
| The two reference repos `/project/src/ck8s-dev` and `/project/src/awesome-multirepo-workshop` | **MUST NOT modify.** Read-only models this repo was derived from (Scope OUT). Copy patterns; never patch them. |

Two things the table cannot protect, because they bypass `just` entirely:

- **`workshop` and `lxc` work directly from the host.** The guards above are
  conventions in recipes, not an enforcement boundary. `workshop remove
  <name>` destroys an instance no matter how it was launched.
- **`git` works in every clone under `/project/git`.** A clone is a real
  checkout: never force-push, never push as a side effect of unrelated work.

### Add a repository to a profile

1. Edit `config/repos/<profile>.json` and append to `core_repos` or
   `supporting_repos` an entry shaped
   `{"name": "<dir-name>", "forge": "github|opendev|launchpad", "url": "<clone-url>"}`,
   plus optional `"fork_of": "<owner>/<repo>"` for a GitHub fork workflow.
2. Apply from the host: `just repos <profile>` (guarded). Clones land under
   `/project/git/<name>`; existing clones are fetched and fast-forwarded,
   never re-cloned; dirty clones are reported and left untouched.
3. Forge behavior: `github` clones via `gh repo clone` and adds a `fork`
   remote when `fork_of` is set (needs `github_handle` in config); `opendev`
   clones over https, then `git review -s` wires the Gerrit remote
   (`gitreview.username` from `config.gerrit_username`, else the host user
   name); `launchpad` clones over https.
4. `just lint` validates the JSON (`config/**/*.json` is parsed by the
   config-validate gate).

### Add a profile

Profiles are data; adding one never touches the render code (D-13/D-14).

1. `profiles/<name>/workshop.yaml.j2` - compose it ONLY from the shared
   partials, in the existing templates' include order (see the
   `profile-authoring` skill for the contract). Then symlink every
   `profiles/_partials/*.yaml.j2` into `profiles/<name>/partials/` as a git
   symlink (`../../_partials/<file>`); `scripts/render.sh` refuses to render
   when a link is missing or broken.
2. `profiles/<name>/vars.json` - profile defaults: snap pins (`snaps`), tox
   (`tox`), interpreter list (`pythons`), extra store SDKs (`extra_sdks`,
   inserted between `uv` and the project SDK), and the `core_repos` seed.
3. `.workshop/<name>-tools/` - the in-project SDK: `sdk.yaml`
   (`name: <name>-tools`, `base: ubuntu@26.04`) plus `hooks/` (`setup-base`,
   `setup-project`, `check-health`; see Invariant 2 and the `hook-authoring`
   skill). The shared `sdks-chain` partial lists `project-<name>-tools` last
   automatically from the `profile` var.
4. `config/repos/<name>.json` - the repo list for `just repos <name>`
   (seed it from the `core_repos` in the new `vars.json`).
5. Validate: `just render <name>`, then
   `bash scripts/check-render.sh .workshop/<name>.yaml` against the vendored
   schema, then `just lint`. Add the profile and one suffixed instance to
   the bounded `NAMES` list in `scripts/ci/render-matrix.sh` so CI renders
   it.
6. Name rules: `^[a-z](?:-?[a-z0-9])*$`, max 40 chars. Profiles and instances
   share one namespace: a new `profiles/<name>/` that matches a launched
   `.workshop/<name>/` shadows that instance - renders warn
   (`shadow_warning`) instead of failing (D-13).

## Invariants

All agents operating in this repo MUST obey the following invariants.

### 1. No secrets in the repository - and the `GITHUB_TOKEN` trap

- **Rule**: credentials never live in the repo, the rendered yaml, a
  template, or a docs example. The GitHub token is stored in the HOST
  keyring by `just secret-setup` (`scripts/secret-setup.sh`, service
  `sunbeam-workshop-github-token`); the rendered `system:github-token`
  secret slot carries keyring LOOKUP attributes (`service: "gh:github.com"`,
  `username: ""`), never the value. `.state/` (mode 0700) and
  `.openchamber-password` are gitignored.
- **CRITICAL TRAP**: `GITHUB_TOKEN` and `GH_TOKEN` MUST NEVER be exported in
  the host shell or the container environment. `gh` prefers them over its
  stored keyring login, so a stale or over-broad value silently overrides
  authentication and breaks standard `gh` commands (ck8s-dev rules 10/11;
  `scripts/secret-setup.sh` header).
- The token is never printed: `secret-setup.sh` reads it hidden (`read -rs`)
  and pipes it via stdin only, into the keyring and into
  `gh auth login --with-token`.

### 2. The five-hook contract (root pre-mount vs user post-mount)

Workshop runs five SDK lifecycle hooks (upstream SDK-internals reference;
full semantics in the `hook-authoring` skill):

| Hook | Runs as | When | Key constraint |
| --- | --- | --- | --- |
| `setup-base` | root | launch/refresh, after the base image unpacks, BEFORE the project dir is mounted and plugs/slots connect | Fully self-contained: `/project` is NOT mounted |
| `setup-project` | the `workshop` user | launch/refresh/restore, after mount + auto-connect, before Ready | cwd is `/project` |
| `save-state` | root | refresh/restore, before the old workshop is destroyed | Comes from the OLD revision; `$SDK_STATE_DIR` only exists for this pair |
| `restore-state` | root | refresh/restore, after ALL `setup-project` hooks | Comes from the NEW revision |
| `check-health` | root | launch: after all `setup-project`; refresh/restore: after all `restore-state` | Reports `workshopctl set-health` (`okay`/`waiting`/`error`) |

Repo rules on top of the contract:

- This repo's in-project SDKs ship `setup-base`, `setup-project`, and
  `check-health` under `.workshop/<profile>-tools/hooks/` as executable bash
  with a shell shebang (non-shell payloads such as `tox-requirements.txt`
  share the directory and are skipped by the shellcheck gate).
- `setup-project` SOURCES `/project/scripts/hooks/lib-common.sh`; the shared
  provisioning steps live there and are never duplicated into a hook.
- Provisioning failures in `setup-project` are loud but non-fatal
  (`run_step`): `check-health` is the authoritative gate. Every failure path
  in `check-health` calls `workshopctl set-health --code=<reason> error`
  with a message and exits non-zero; the hook ends with `set-health okay`.

### 3. Rendered files are generated - edit templates, not outputs

- `.workshop/<name>.yaml` is rendered by `scripts/render.sh` from
  `profiles/<profile>/workshop.yaml.j2` plus the merged vars doc
  (jinja2-cli; atomic publish; post-validated: YAML parses, top-level `name`
  equals the instance name, `base` is present). It is gitignored.
- `.state/<name>.vars.json` is the persisted merged vars doc (mode 0600)
  written by `scripts/setup.sh`; hooks read identity from it.
- `scripts/vm/cloud-init.yaml.j2` is rendered fresh from the merged vars doc
  on every `just vm-create`.
- Never hand-edit an output: change the template or vars and re-run
  `just render <name>`. CI renders the bounded matrix
  (`scripts/ci/render-matrix.sh`) and validates against the vendored schema
  (`scripts/check-render.sh`), so a hand edit is both overwritten and
  detected.

### 4. IS-7 guarded recipes - `assert-host`

Every destructive or host-mutating recipe carries the `assert-host` guard
(recipe in `Justfile`). The guarded list, by IS-7 category:

- **Host-mutating setup steps**: `setup` (render + `.state` write + keyring
  + launch).
- **Keyring writes**: `secret-setup` (host keyring storage, host `gh` login,
  secret-plug wiring).
- **Sidecar-VM lifecycle**: `vm-create`, `vm-destroy`.
- **Repo-list mutation**: `repos` (clones/updates the per-profile
  checkouts).

The guard refuses when `$USER` is `workshop` (inside a workshop container,
where sudo is passwordless), on a non-Ubuntu host, and when no working LXD
answers. `I_KNOW_WHAT_IM_DOING=1` bypasses the guard; never set it to make a
refusal go away. The container is not a security boundary: `/project` is
mounted writable, and host recipes run later from this same tree - read
`git diff` before running guarded recipes on the host after container
activity.
